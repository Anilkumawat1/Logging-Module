# Spring Boot Production Logging Starter

A reusable Spring Boot 3 starter for request logging, structured application logs, sensitive-data masking, and MDC context propagation across asynchronous work.

The central guarantee is explicit:

> When a request starts async work through the provided `TaskDecorator`, wrapped `ExecutorService`, or wrapped `CompletableFuture` executor, logs inside child and nested tasks retain the original request, trace, user, service, and allowed custom MDC context.

## Modules

- `starter`: reusable library artifact, `com.anil:spring-boot-production-logging-starter`
- `examples/demo-app`: runnable demo with HTTP, business, error, `@Async`, and nested executor examples

## Installation

```xml
<dependency>
  <groupId>com.anil</groupId>
  <artifactId>spring-boot-production-logging-starter</artifactId>
  <version>0.1.0-SNAPSHOT</version>
</dependency>
```

For JSON console output using the bundled Logback include, add:

```xml
<dependency>
  <groupId>net.logstash.logback</groupId>
  <artifactId>logstash-logback-encoder</artifactId>
</dependency>
```

## Architecture

```text
HTTP request
  -> HttpLoggingFilter installs request/user/trace fields in MDC
  -> HTTP filter writes a structured HTTP_REQUEST event
  -> normal controllers and services keep using SLF4J
  -> LoggingTaskDecorator or LoggingExecutors captures MDC
  -> worker thread restores captured context, runs task, restores previous MDC
  -> HTTP filter writes a structured HTTP_RESPONSE event and clears/restores MDC
```

Customizable SPIs:

- `UserIdentityProvider`
- `SensitiveDataMasker`
- `ClientIpResolver`
- `OperationResolver`
- `HttpLogWriter`
- `TraceContextProvider`
- `LoggingContextManager`

## Configuration

```yaml
spring:
  application:
    name: order-service

app:
  logging:
    enabled: true
    service-name: order-service
    environment: prod
    format: json
    include:
      request-headers: true
      response-headers: true
      request-parameters: true
      request-payload: true
      response-payload: false
      user: true
      ip: true
      domain: true
      url: true
      operation: true
      trace: true
      thread: true
      logger: true
      caller: false
    payload:
      request-max-size: 10000
      response-max-size: 10000
      log-binary: false
    request-payload:
      on-status-ranges:
        - "400-599"
    masking:
      enabled: true
      replacement: "***"
    ip:
      headers:
        - X-Forwarded-For
        - X-Real-IP
        - CF-Connecting-IP
    excluded:
      paths:
        - /actuator/health
        - /actuator/prometheus
      methods:
        - OPTIONS
      content-types:
        - multipart/form-data
        - application/octet-stream
        - application/pdf
        - image/
        - video/
        - audio/
    operations:
      mappings:
        "POST /api/orders": CREATE_ORDER
    categories:
      HTTP_REQUEST: true
      HTTP_RESPONSE: true
      APPLICATION: true
      BUSINESS: true
      SECURITY: true
      ERROR: true
    context:
      propagation:
        enabled: true
        allowed-fields:
          - request_id
          - trace_id
          - span_id
          - user_id
          - role_ids
          - authenticated
          - service
          - environment
          - tenant_id
    identity:
      user-id-claims:
        - user_id
        - sub
      role-id-claims:
        - role_ids
        - roles
    async:
      enabled: true
      task-decorator: true
      executor-integration: true
```

`service-name` falls back to `spring.application.name`, then `unknown-service`. `environment` falls back to the active Spring profiles, then `default`.

## HTTP Logging

`HttpLoggingFilter` emits logs in this order for every non-excluded request:

1. `HTTP_REQUEST`: request metadata, masked request headers, and masked query parameters
2. application/business/security/integration logs generated by your code
3. `HTTP_RESPONSE`: response status, duration, masked response headers, response payload when enabled, and request payload when the configured status rule matches

HTTP events can include:

- `request_id`, `trace_id`, `span_id`
- `authenticated`, `user_id`, `role_ids`
- `ip`, `domain`, `url`, `endpoint`, `operation`, `method`
- masked request/response headers
- masked query parameters
- bounded request/response payloads
- status and duration in milliseconds

Request payloads are omitted for successful responses by default and included for `400-599`, subject to masking and size limits.

Binary and large body protections are enabled by default. Multipart, octet-stream, PDF, image, video, and audio content are not logged unless `app.logging.payload.log-binary=true`.

## Request IDs And Trace IDs

The filter uses `X-Request-ID`, then `X-Correlation-ID`, then generates a UUID. Trace IDs are read from existing MDC, W3C `traceparent`, B3 headers, or `X-Trace-Id`.

Normal SLF4J logs are enriched through MDC:

```java
private static final Logger log = LoggerFactory.getLogger(OrderService.class);

log.info("Creating order");
```

With a JSON or text Logback config that includes MDC, this log carries the same `request_id`, `trace_id`, `user_id`, role_ids, service, and environment as the HTTP event.

## Logback Output

JSON:

```xml
<configuration>
  <include resource="com/anil/logging/logback/logback-production-json.xml"/>
</configuration>
```

For your products, use the JSON include above. The starter still contains a text include for local experiments, but the demo app and default formatter are JSON-first.

Text:

```xml
<configuration>
  <include resource="com/anil/logging/logback/logback-production-text.xml"/>
</configuration>
```

Use standard Logback appenders for console, file, rolling file, and async appenders. For Datadog, ELK, GCP, Loki, and Splunk, ship the JSON output through your normal agent/sidecar/collector and map MDC fields directly.

## Structured Logging API

SLF4J remains the default developer API. For event-specific structured fields:

```java
loggingService.info(
    LogCategory.BUSINESS,
    "Order created",
    Map.of("order_id", order_id, "amount", amount)
);
```

Fluent API:

```java
loggingService.info("Order created")
    .category(LogCategory.BUSINESS)
    .field("order_id", order_id)
    .field("amount", amount)
    .log();
```

Timer API:

```java
try (TimerContext ignored = loggingService.timer("ORDER_PROCESSING")) {
    processOrder();
}
```

Audit logs are separate:

```java
auditLogger.log("DELETE_PRODUCT", Map.of("product_id", product_id));
```

Do not put event-specific fields such as `order_id` or `payment_id` into global MDC unless they truly define a scoped context. Prefer:

```java
try (LoggingContextScope ignored = LoggingContext.with("tenant_id", tenant_id)) {
    log.info("Processing tenant");
}
```

## Thread Context Propagation

MDC is backed by `ThreadLocal`; it does not automatically move to worker threads.

This works automatically when Spring Boot creates the application task executor and `app.logging.async.executor-integration=true`:

```java
@Async
public CompletableFuture<Void> process() {
    log.info("Still has request_id");
    return CompletableFuture.completedFuture(null);
}
```

For a custom Spring executor:

```java
@Bean
ThreadPoolTaskExecutor orderExecutor(LoggingTaskDecorator decorator) {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(5);
    executor.setMaxPoolSize(20);
    executor.setQueueCapacity(100);
    executor.setTaskDecorator(decorator);
    executor.initialize();
    return executor;
}
```

For plain Java executors:

```java
ExecutorService executor = LoggingExecutors.wrap(
    Executors.newFixedThreadPool(8),
    loggingContextManager
);

executor.submit(() -> log.info("Background processing"));
```

For `CompletableFuture`:

```java
CompletableFuture.runAsync(
    () -> log.info("Processing"),
    LoggingExecutors.wrap(existingExecutor, loggingContextManager)
);
```

This is not guaranteed:

```java
CompletableFuture.runAsync(task);
```

That uses the JVM common pool and arbitrary worker threads; the starter cannot promise MDC propagation there.

## Scheduled Work

Request-originated scheduled work can propagate request context only when submitted through a wrapped/decorated scheduler. Independent `@Scheduled` jobs do not have an HTTP request and should not receive a fake request ID. Add your own execution ID or trigger field if that is useful:

```java
try (LoggingContextScope ignored = LoggingContext.with("trigger", "SCHEDULED")) {
    log.info("Cleanup started");
}
```

## Masking

The default masker recursively masks JSON fields such as `password`, `token`, `access_token`, `refresh_token`, `api_key`, `client_secret`, `card_number`, `cvv`, `cvc`, private keys, and similar secrets. Header and query-parameter matching is case-insensitive. Invalid JSON falls back to bounded text masking.

CVV/CVC values should never be logged. Authorization, cookies, API keys, and auth tokens are masked by default.

## Authentication, JWT, OAuth2

If Spring Security is present, `DefaultUserIdentityProvider` reads the current `Authentication`. For JWT/OAuth2 tokens it first reads `user_id` and `role_ids` claims, then falls back to `sub`, `roles`, `scope`, `scp`, and finally Spring Security authorities. Override `UserIdentityProvider` when your application needs tenant-aware identity or a different claim mapping.

## Operations

Resolution order:

1. `@LogOperation("CREATE_ORDER")`
2. YAML mapping such as `"POST /api/orders": CREATE_ORDER`
3. HTTP method fallback: `POST=CREATE`, `GET=READ`, `PUT/PATCH=UPDATE`, `DELETE=DELETE`
4. endpoint fallback

## Extension Notes

- Database logging is intentionally an extension point; SQL and bind parameters are not dumped by default.
- Integration logging should use `LogCategory.INTEGRATION` and avoid propagating authorization material.
- Error logging includes exception type, masked/truncated message, and bounded stack trace for structured events. HTTP responses are not modified to expose stack traces.

## Demo

Run:

```bash
mvn -pl examples/demo-app spring-boot:run
```

Endpoints:

- `GET /api/users`
- `POST /api/orders`
- `GET /api/orders/{id}`
- `POST /api/error`
- `POST /api/async`

`POST /api/async` starts nested executor and `@Async` work. Logs should be searchable by one `request_id`.

## Troubleshooting

- Missing `request_id` in child threads: verify the task uses `LoggingTaskDecorator`, `LoggingExecutors.wrap(...)`, or an explicitly wrapped `Runnable`/`Callable`.
- Missing JSON fields in normal SLF4J logs: verify Logback includes MDC or the provided JSON/text include.
- Raw secrets in logs: add the field/header/query name to `app.logging.masking.*` and keep payload logging bounded.
- Proxy IP concerns: only trust forwarded IP headers from trusted proxies/load balancers. Otherwise use `request.getRemoteAddr()`.
- Caller class/method: prefer logger name. Stack inspection is intentionally not enabled by default because it adds cost to every log.
